# Fire 재설계 — 검증되는 레이아웃 엔진

작성 2026-08-27

## 1. 배경

2026-08-27 아침, 재부팅 후 Fire가 메뉴바 아이콘을 전부 없앴다. 실측 결과는 이렇다.

- Fire는 정상 실행 중이었다(PID 1484, 로그인 시각부터).
- 내장 화면 1470pt에서 status item 창이 4개만 남아 있었다(배터리, Itsycal, 제어 센터, 시계). 나머지 17개는 화면 밖으로 밀려 있었다.
- `layout.json`이 지정한 숨김 대상은 3개(WorkspaceShelf, AudioVideoModule, MenubarX)뿐이었다.
- Fire 자신의 아이콘도 밀려나 있었다. 설정창을 열 수단이 사라졌다.
- 그런데 `recovery.json`에는 성공으로 기록돼 있었다.

```json
"lastRebuildResult" : "applied: main=21 fireBar=3",
"consecutiveFailures" : 0
```

저장돼 있던 위치값은 다음과 같았다.

```
NSStatusItem Preferred Position FireSeparatorItem = 307    → 경계 x=1163
NSStatusItem Preferred Position FireControlItem   = 2525   → 어떤 화면 폭으로도 불가능
```

`2525`는 "화면 오른쪽 끝에서의 거리"인데 내장 1470pt, 외부 1920pt 어느 쪽도 그만큼 넓지 않다. 이 값이 남아 있는 한 Fire 아이콘은 매 로그인마다 모든 항목의 최좌단에 앉고, 경계가 어디에 있든 자기 숨김 구간 안으로 들어간다.

`diag.realign`을 보냈더니 저장값은 307에서 454.5로 바뀌었으나 실제 배치는 그대로였다. HANDOFF 5.2가 "재정렬에서 수렴 확인"이라고 적어둔 자기수복은 이 상황에서 작동하지 않았다.

## 2. 근본 원인

**Fire는 자기가 한 일의 결과를 확인하지 않는다.**

`applySections()`는 `collapse()`를 호출한 뒤 곧바로 성공을 기록한다. 메뉴바를 다시 재보지 않는다. 그래서 실패를 실패로 인식하지 못한다.

여기서 나머지가 파생된다.

1. **쓸 수는 있는데 읽을 수가 없다.** 숨김은 공개 API가 아니다. `NSStatusItem Preferred Position <autosaveName>`이라는 비공개 defaults 키에 값을 쓰고, 구분자 status item 폭을 화면 너비만큼 늘려 왼쪽 항목을 화면 밖으로 밀어내는 방식이다. macOS는 결과를 돌려주지 않는다. 확인하려면 메뉴바를 다시 측정하는 수밖에 없다.

2. **흔들리는 측정으로 다시 쓴다.** 위치 계산은 접근성 프레임과 CGWindow 좌표에서 나온다. 그 측정은 AX 0.25초 타임아웃, 제어 센터가 모든 소유 PID를 가리는 문제, 노치 은폐, 디스플레이별 복제 때문에 수시로 항목을 놓친다. 놓친 측정이 잘못된 경계를 낳고, 그 경계가 다시 측정 대상을 바꾼다. 노이즈가 들어간 닫힌 루프라 가만히 둬도 표류한다.

3. **잘못된 값이 디스크에 남아 재부팅을 넘어간다.** 위 `2525`가 그 예다.

4. **불변식도 안전모드도 없다.** 계산이 한 번 틀리면 전면 장애가 되고, 설정창이 그 숨겨진 아이콘 뒤에 있어서 앱 안에서 손쓸 방법이 사라진다.

5. **검증한 적 없는 경로에서 터졌다.** HANDOFF 5.1이 미검증으로 남겨둔 외부 모니터 연결 상태였다. `alignSeparator()`는 두 화면 항목을 절대 x 좌표로 한 줄에 세운다. 내장(0~1470)과 외부(1470~3390)가 섞이면 경계가 엉뚱한 화면 기준으로 잡힌다.

구조가 틀린 게 아니라 실행이 틀렸다. Ice도 같은 구분자 메커니즘을 쓴다.

## 3. 목표

사용자가 정의한 요구는 다음 여섯 개다.

1. 메뉴바에 보일 항목을 고른다.
2. 나머지는 Fire Bar에 들어간다.
3. Fire Bar 패널을 드래그로 옮길 수 있고, 위치를 기억한다. 기본 위치는 메뉴막대 바로 아래.
4. 메뉴막대 안에서 항목 순서를 바꿀 수 있다 — macOS의 `⌘`+드래그가 이미 제공한다. Fire는 대행하지 않고, **무엇을 어디로 끌어야 하는지 알려준다.**
5. Fire Bar 안에서 항목 순서를 바꿀 수 있다.
6. 외부 모니터를 연결해도 내장 화면과 똑같이 보인다. 이것이 기본값이다.

## 4. 비목표

- 화면마다 다른 분류. 구분자 폭이 하나뿐이라 불가능하다.
- "외부 모니터에서는 전부 표시" 옵션. **보류.** 실현 가능성 계산은 부록 A에 남긴다.
- 남의 앱을 종료·재실행해 순서를 강제로 바꾸는 것. 앱마다 샌드박스 경로가 다르고, 재실행에 실패하면 사용자 앱이 죽은 채 남는다.

## 5. 원리 — 변하지 않는 것

macOS는 남의 status item을 숨기거나 옮기게 해주지 않는다. 공개 API로 가능한 것은 하나뿐이다. 내 status item의 폭을 화면 너비만큼 늘리면 그 왼쪽 항목들이 화면 밖으로 밀려난다.

```swift
func collapse() { separatorItem.length = maxCollapsedLength() }  // 가장 넓은 화면폭 + 200
func expand()   { separatorItem.length = 1 }
```

그래서 구분자는 경계 표식이다. 왼쪽이 숨김(FIRE_BAR), 오른쪽이 표시(MAIN)다. 평소 폭이 1이라 눈에 보이지 않는다.

**여기서 나오는 제약 하나:** 숨김은 왼쪽부터 이어진 연속 구간에만 걸린다. 물리 순서가 `A B C D E`인데 `A`와 `D`만 보이고 싶다면, 먼저 `B C E A D` 순으로 만든 뒤 `B C E`를 Fire Bar로 보내야 한다. 순서를 맞추는 일은 사용자가 `⌘`+드래그로 한다. Fire가 할 일은 **어떤 항목을 어디로 옮겨야 연속이 되는지 계산해서 문장으로 알려주는 것**이다. 이것이 요구 4번의 실제 내용이다.

## 6. 아키텍처 — 3단 분리

지금은 측정·계산·적용이 한 덩어리로 얽혀 있어서 중간에 실패해도 티가 나지 않는다. 세 단계로 분리하고, 각 단계가 실패를 위로 전달하게 한다.

### 6.1 측정 (Survey)

한 번의 완전한 스캔으로 진실을 확정한다. 부분 결과를 반환하지 않는다.

- `expand()` 상태에서만 수행한다. 숨긴 상태의 좌표는 믿을 수 없다.
- 화면별로 나눈 행을 만든다. 기준 행은 주 디스플레이.
- **분류된 항목 중 하나라도 못 찾으면 실패를 반환한다.** 지금처럼 놓친 항목을 빼고 계속 진행하지 않는다.

### 6.2 계획 (Plan)

측정 결과와 사용자 분류로부터 목표 상태를 계산한다. 부작용이 없어서 단위 테스트가 가능하다.

- 구분자 위치값
- Fire 아이콘 위치값
- 연속이 아닌 분류가 있으면, 연속으로 만들기 위한 `⌘`+드래그 안내 문장

### 6.3 적용과 검증 (Apply & Verify)

쓰고, 다시 재서, 맞는지 확인한다.

1. 위치값을 쓰고 `collapse()`한다.
2. 배치가 잡힐 시간을 준 뒤 다시 측정한다.
3. 실제로 보이는 항목 집합이 MAIN 지정 집합과 같은지 비교한다.
4. 다르면 1번으로 돌아간다. 최대 3회.
5. 3회 실패하면 `expand()`한 상태로 고정하고 사용자에게 알린다.

## 7. 불변식

코드가 어기지 못하게 강제한다.

1. **MAIN으로 지정된 항목은 구분자 왼쪽에 놓이지 않는다.** Fire 자신의 아이콘도 이 규칙의 한 사례다. 다만 어겼을 때 대가가 가장 크다 — 사용자가 앱에 닿을 수단을 통째로 잃는다.
2. **위치값은 `0 ≤ v ≤ 해당 화면 폭` 범위 안이다.** 벗어나는 값은 쓰지 않는다. 실행 시작 시 저장값도 검사해 범위 밖이면 삭제하고 기본 위치로 되돌린다.
3. **검증에 3회 실패하면 펼친 상태로 고정한다.**

### 7.1 Fire 아이콘의 두 가지 숨김 — 구분할 것

| 경우 | 방식 | 결과 |
|---|---|---|
| 의도한 숨김 (사용자가 FIRE_BAR로 지정) | `fireItem.isVisible = false` | Fire Bar 패널 안에 불꽃 버튼이 그려진다. `opt+cmd+F`로 열린다. 돌아올 길이 있다 |
| 사고 (구분자가 Fire 오른쪽에 앉음) | 화면 밖으로 밀림 | Fire는 자기가 보인다고 믿는다. 버튼이 없다. 설정창도 못 연다 |

앞의 것은 지원해야 할 기능이다. 막으면 안 된다. 불변식 1이 막는 것은 뒤의 것이다.

## 8. 실패 정책

실패 상태 둘 중 하나를 골라야 한다.

- **접힌 채 틀림** — 2026-08-27 아침 상태. 아이콘 17개 실종, 설정창 접근 불가, 사용자가 손쓸 방법 없음.
- **펼친 채** — 숨김 기능만 안 됨. 맥은 정상, 설정창 열림, 사용자가 직접 고칠 수 있음.

**쓸 수 있는 쪽으로 실패한다.** 현재 코드는 반대쪽으로 실패한다.

전체 해제는 첫 대응이 아니라 마지막 수단이다. 첫 대응으로 전체를 해제하면 사용자가 진짜 숨기려던 항목까지 튀어나온다. 6.3의 재시도를 모두 소진한 뒤에만 펼친 상태로 고정한다.

## 9. 고칠 것

### 9.1 쓴 뒤 검증

`applySections()` 이후 재측정해 실제 결과를 확인한다.

- 완료 기준: 숨겨진 항목 집합이 FIRE_BAR 지정 집합과 정확히 일치할 때만 성공으로 기록한다.
- `recovery.json`에 의도가 아니라 실측 결과를 적는다. 현재는 `"applied: main=21 fireBar=3"`처럼 의도만 적혀 있다.

### 9.2 불완전한 스캔으로 경계 계산 금지

`alignSeparator()`는 분류된 모든 항목이 스캔에 나타났을 때만 실행한다.

- 하나라도 없으면 중단하고 직전 경계를 유지한다. 사유를 기록한다.
- 현재는 놓친 항목을 제외한 채 `lastIndex(where:)`를 계산해 경계가 오른쪽으로 밀린다. 2026-08-27 사고의 직접 원인이다.

> 이전 논의에서 `alignSeparator()`를 삭제하자고 했던 제안은 철회한다. 사용자가 분류를 바꾸면 경계가 따라와야 하므로 자동 계산은 필요하다. 문제는 계산 자체가 아니라 검증 없는 계산이다.

### 9.3 화면별 분리

`alignSeparator()`가 `discoveredItems.sorted { $0.frame.minX < $1.frame.minX }`로 두 화면 항목을 한 줄에 세운다. 내장(0~1470)과 외부(1470~3390)가 섞인다.

- 화면별로 행을 나누고, 기준 행 하나만 쓴다.
- 기준 행 선택은 결정적으로 — 주 디스플레이 우선.

### 9.4 위치값 범위 검사

- 쓰기 전에 `0 ≤ value ≤ 해당 화면 폭`을 검사한다. 벗어나면 쓰지 않는다.
- 실행 시작 시 `FireControlItem`과 `FireSeparatorItem` 저장값을 검사한다. 범위 밖이면 삭제하고 기본 위치에서 시작한다.
- 완료 기준: `2525` 같은 값이 다시 저장되지 않는다.

### 9.5 불연속 안내를 구체적으로

분류가 물리 순서상 연속이 아닐 때, 연속으로 만들려면 무엇을 어디로 옮겨야 하는지 계산해 문장으로 제시한다.

- 현재: "macOS 제한, `⌘`+드래그" (무엇을 어디로인지 없음)
- 목표: "MenubarX를 Owly 왼쪽으로 `⌘`+드래그하세요."

이것이 이 앱의 핵심 가치다. 사용자가 직접 해야 하는 추론을 앱이 대신한다.

### 9.6 외부 모니터에서 동일 표시 (기본값)

현재 동작을 유지한다. 구분자 폭이 `가장 넓은 화면 + 200`이라 양쪽에 똑같이 걸린다. 9.3을 고친 뒤 실측으로 재확인한다.

## 10. 새로 만들 것

### 10.1 Fire Bar 패널 드래그 이동

- 패널을 드래그로 옮길 수 있다.
- 위치를 화면별로 저장한다.
- 저장된 위치가 없으면 현재 동작을 쓴다 — 클릭 지점 기준, 메뉴막대 바로 아래(`FireBarPositioner.swift`).
- 화면 밖으로 나가지 않게 보정한다. 디스플레이 구성이 바뀌어 저장 위치가 화면 밖이 되면 기본 위치로 되돌린다.

### 10.2 Fire Bar 내부 항목 재정렬

- 드래그로 순서를 바꾸고 `layout.json`에 저장한다.
- 우리 패널이라 macOS 제약이 없다.

## 11. 검증 계획

측정 없이 고쳤다고 주장하지 않는다. HANDOFF 6절 5번의 반복을 막는다.

1. 위치값 초기화 후 재실행을 3회 반복한다. 매번 숨겨진 집합이 지정과 일치하는지 확인한다.
2. 외부 모니터 연결과 해제를 반복한다. 매번 확인한다.
3. 잠자기 복귀 후 확인한다.
4. 클램셸(내장 닫기) 상태에서 확인한다.
5. Fire를 FIRE_BAR로 지정했을 때 불꽃 버튼과 `opt+cmd+F`가 동작하는지 확인한다.

측정은 layer 25 status item 창을 직접 열거하는 스크립트로 한다. 앱의 자체 보고를 믿지 않는다.

## 부록 A — 보류된 "외부 모니터에서는 전부 표시" 옵션

보류하지만 계산은 남긴다. 나중에 되살릴 때 다시 재지 않기 위해서다.

원리: 구분자 폭은 하나인데 화면 폭은 다르다. 그 차이를 쓴다.

2026-08-27 실측값(Fire 종료 상태):

```
내장   1470pt,  노치 646~825
외부   1920pt,  노치 없음
항목   11개, 총 584pt   (양쪽 동일 — 미러 확인)
```

구분자 폭을 `L`이라 하면,

- 내장에서 숨으려면 왼쪽 그룹이 노치(x=825)까지 밀려야 한다: `L > 645 - MAIN폭`
- 외부에서 보이려면 왼쪽 끝이 화면 안이어야 한다: `L ≤ 1920 - 584 = 1336`

MAIN에 5개를 남긴다면(WiFi 38 + 배터리 71 + Itsycal 93 + 제어 센터 42 + 시계 109 = 353pt):

```
L ∈ (292, 1336]      여유 1044pt
```

노치가 없는 화면이면 `L ∈ (886, 1336]`, 여유 450pt. 좁지만 성립한다.

조건 세 개:

1. 외부가 내장보다 넓어야 한다. 좁으면 반대가 된다 — 설정에서 회색 처리.
2. 항목 개수가 바뀌면 `L`을 다시 계산해야 한다. 6.3의 검증 루프가 처리한다.
3. 완전 미검증 경로다. 만들면 실기기 확인이 필수다.
